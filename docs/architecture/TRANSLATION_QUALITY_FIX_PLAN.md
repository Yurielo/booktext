# План исправления качества перевода BookText

Цель — уменьшить обнаруженные ошибки перевода и предотвратить их незаметное попадание в готовую книгу, сохранив локальную модель `qwen3:8b`. Исправления должны работать в существующем translation workflow, сохранять исходники, иллюстрации и возможность продолжения с checkpoint.

Статус: план подготовлен по запросу пользователя. Этот документ не утверждает, что изменения реализованы или качество полного перевода принято. Полный перевод книги не запускать на этапе разработки и пилота.

## Основания и границы

Проверенная исходная реализация: `tools/translation.py`, `tests/test_translation.py`, `docs/architecture/TRANSLATION_LAYER.md`; baseline Core `97ebeab12c95f87e48e015322ede791eb37fc512`.

Фактические ошибки прежнего перевода: `DEDICATION → ВСАДНИК`, `Magic Wand → Магический палец`, `priestess → иеродоложницу`. Отдельный короткий эксперимент с анализом контекста дал правильные два заголовка, но не доказал качество всей книги; русский текст всё ещё требовал редакторской оценки. Одновременно изменялись prompt, контекст и режим рассуждения, поэтому улучшение нельзя приписывать одному параметру.

В production уже есть соседний контекст, словарь, logical-unit ownership, checkpoints, проверки чисел и исходных отпечатков. Их нужно усилить, не создавать второй переводчик.

В scope: подготовка запросов, проверка ответов, ограниченные повторы, provenance и resume, machine protocol и необходимые сообщения состояния в приложении, регрессионная проверка подготовки текста и итогового DOCX. Исправления extraction/export допустимы только при воспроизведённой регрессии, непосредственно мешающей этому workflow.

Вне scope: замена модели, облачный провайдер, новый OCR, новая классификация изображений, общий редизайн приложения, автоматическая правка raw OCR, research table reconstruction.

## 1 Воспроизвести ошибки и зафиксировать образец

- Сохранить небольшую выборку реальных source units с IDs, source hashes, порядком, типом блока, заголовками раздела и исходными ответами модели.
- Включить посвящение, магический жезл, жрицу, конденсатор флюида, числа и ссылки, абзац с продолжением между страницами 43–45, короткий заголовок, список и отрицание.
- Добавить отрицательные примеры для проверок: допустимое неизменённое имя/идентификатор, латинский термин, естественное совпадение перевода с соседним контекстом, допустимое изменение количества предложений.
- Сначала локально воспроизвести текущие дефекты проверки без inference. Реальную сравнительную пробу проводить позже на одной фиксированной выборке.

Результат этапа: воспроизводимые случаи, ожидаемые структурные результаты и явно указанные семантические критерии. Ожидаемые русские формулировки остаются критериями пилотной оценки, а не универсальным механизмом автоматической подстановки.

## 2 Разделить сохранение и качество

- Отдельно учитывать успешность запроса, структурную валидность, целостность checkpoint и quality review.
- Сохранять корректно полученный проблемный ответ вместе с сигналами; сохранение не означает одобрение смысла.
- Проверять завершённость ответа, причину окончания генерации, типы полей, непустой текст, лимит ответа и соответствие owned unit.
- Не записывать `context_only_output: PASS` без проверки. Различать доказанную правильность списка IDs и непроверенную возможность включения соседнего текста внутрь ответа.
- Добавить проверку непереведённых коротких заголовков, неожиданных повторов и смешения алфавитов. Имена и идентификаторы должны иметь исключения на основании источника.
- Числа, дроби, единицы и ссылки сверять с источником. Заранее определить разрешённые эквивалентные представления; не считать любое изменение десятичного разделителя доказанным искажением.
- Отношение длин, различия числа предложений, возможную потерю отрицания и совпадения с соседним текстом использовать как сигналы, а не самостоятельное доказательство смысловой ошибки.

Результат этапа: никакого ложного «качество PASS». Техническое завершение и наличие нерешённых проблем качества видны отдельно; готовый к просмотру черновик не обозначается как проверенный человеком.

## 3 Улучшить контекст запроса

- Ввести версию prompt и явный контракт: document context, read-only context before, owned source, read-only context after.
- Передавать тип блока, достоверную иерархию заголовков, название и автора из metadata. Не придумывать жанр или назначение неизвестного блока.
- Подбирать соседний контекст по полным предложениям/блокам в пределах рассчитанного бюджета. Учитывать размер самого source unit, словаря и ожидаемого ответа.
- Сохранять целые логические единицы; физические границы страниц не являются границами перевода. Слишком большой unit требует явной обработки бюджета, а не скрытого обрезания.
- Для заголовка посвящения применять контекст роли в книге; для обычного слова dedication сохранять возможность иного перевода.
- Использовать полные названия языков, точное требование сохранения смысла и запрет на пересказ. Контекст не входит в публикуемый перевод.
- Не считать JSON причиной смысловых ошибок без отдельной проверки. Существующий структурированный ответ сохранить, усилив его валидацию.

Результат этапа: запрос воспроизводим, его версия и использованный контекст отражены в provenance; никаких пропущенных исходных частей из-за лимита контекста.

## 4 Сделать словарь проверяемым

- Поддержать версии словаря, контекст применения, допустимые формы и исключения, сохранив совместимость с текущим JSON source term → target term.
- Передавать только релевантные текущему блоку записи плюс небольшой контекст книги.
- Проверять наличие терминов с допустимыми склонениями и вариантами; неоднозначный случай отмечать для проверки.
- Различать обязательные согласованные термины и предложенные варианты. Новые семантические предпочтения не объявлять пользовательским решением.
- Не выполнять слепую замену терминов в готовой русской фразе.

Результат этапа: нарушения закреплённой терминологии обнаруживаются; допустимые русские формы и омонимы не создают систематических ложных ошибок.

## 5 Ограничить повторные попытки

- Базовый проход сохранить с `think: false`; улучшенный prompt и проверки применяются в нём.
- При конкретной проблеме повторять только соответствующий unit, передавая причину и нужный контекст. Не перезапускать всю книгу.
- Предлагаемый предел — две дополнительные попытки на unit, общий временной и token budget на unit и лимит дополнительных попыток на job. Конкретные значения бюджета выбрать по пилоту и документировать.
- Рассуждение Qwen разрешить только как ограниченный вариант повторной попытки, если пилот подтвердит преимущество. Безусловно включать его для всех блоков не требуется.
- Хранить все варианты и причины выбора. Никакого молчаливого overwrite уже принятого пользователем перевода.
- При неустранённой проблеме сохранить состояние review required; не запускать бесконечные повторы. Технически повреждённый/обрезанный ответ не публиковать как завершённый.
- Реализовать streaming при необходимости для живого прогресса и надёжной отмены. Отдельно проверить server-side прекращение запроса; закрытие Python-клиента само по себе не считать доказательством остановки inference.

Результат этапа: ограниченные затраты, видимые причины повторов, сохранённые ответы и безопасная отмена без влияния на чужие задачи Ollama.

## 6 Обновить fingerprints и resume

- Включить в отпечаток source/CDM, model digest, prompt version, настройки генерации, стратегию контекста, словарь и качество-политику.
- Проверять эти данные и для checkpoints, и при повторном использовании готового manifest; сейчас раннее reuse готового результата не проверяет весь этот набор.
- Отличать несовместимое изменение генерации от обновления проверок: новое правило проверки может перепроверить сохранённый текст без inference; изменение prompt требует новой ревизии генерации.
- Legacy результаты не удалять. До адаптации они сохраняют явную старую версию и статус непроверенных новыми правилами.
- Сохранять завершённые units атомарно, чтобы сбой последнего unit chunk не заставлял переводить уже сохранённые заново. Chunk остаётся единицей сборки и контроля ownership.
- Компактацию выполнять только после проверенной публикации полной сборки и сохранения необходимых вариантов/сигналов/provenance.

Результат этапа: корректный resume, отсутствие смешения старых и новых политик, сохранение истории и решений пользователя.

## 7 Проверить текст и публикацию

- Зафиксировать regression cases для `biomagnetical-ly`, `i. e.`, пропавших пробелов, физических переносов строк и продолжений между страницами.
- Безопасная нормализация работает на производном тексте с source evidence. Не удалять все дефисы и не склеивать разные абзацы по одному внешнему признаку.
- Сборка переведённого документа заменяет только текстовые значения по IDs. Исходные иллюстрации, порядок и привязки сохраняются.
- Проверить DOCX: обычные абзацы без построчных ручных разрывов, настоящие headings/lists, отсутствие внутренних diagnostic labels, пропусков и повторов текста.
- Для книги Бардона учесть уже принятое решение: повреждённую иллюстрацию p407 сохранить; удалить только согласованную титульную картинку, сохранив титульный текст. Проверить hashes остальных изображений.

Результат этапа: исправления качества перевода не ухудшают оформление и сохранность визуального материала.

## 8 Проверки и пилот

Детерминированные tests проверяют контракты и обработку известных ответов: heading/paragraph context, glossary variants, empty/truncated response, numeric mismatch, context leakage signals, retry limits, history, stale fingerprints, per-unit resume, cancellation и отсутствие изменений raw artifacts. Mocks не доказывают качество русского языка.

Реальный пилот использует `qwen3:8b` на 8–12 заранее зафиксированных фрагментах этой книги, включая ранее ошибочные и отдельные контрольные фрагменты. Сравнить старый и новый режим на одинаковом источнике; сохранить ответы, время, число повторов и признаки качества. Для EN↔RU добавить небольшую проверку обратного направления без полного перевода книги.

Измерить memory/process baseline, длительность, token count и время выгрузки модели после success/cancel/timeout. Сохранить bounded keep-alive и изоляцию чужих Ollama jobs; не использовать завершение процессов по имени.

После focused tests запустить полный релевантный Python suite и Swift tests затронутого protocol/UI. Проверить реальные CLI и machine операции translate/validate/resume/export, затем DOCX render и визуальный контроль небольшого образца.

Человеческая приёмка: один небольшой двуязычный DOCX с заголовками, сложными терминами и абзацем через границу страниц. Пользователь оценивает смысл и читаемость; технические PASS не заменяют это решение. Только после принятия образца продолжать полный перевод этой книги с сохранёнными иллюстрациями.

## Критерии завершения

1. Production сохраняет `qwen3:8b`; OCR и облачные модели не запускаются.
2. Известные грубые ошибки отсутствуют в реальном пилоте; результаты проверены по источнику, а не только по сигналам модели.
3. Непереведённые заголовки, обязательная терминология и повреждённые ответы покрыты regression tests.
4. Структурная целостность, качество и human acceptance имеют разные статусы; непроверенные свойства не получают PASS.
5. Повторы и ресурсы ограничены, повторно переводятся только необходимые units; resume и несовместимость версий проверены.
6. Исходники, принятые решения и изображения сохранены; DOCX проходит структурную и визуальную проверку.
7. Реальный образец принят пользователем перед полным новым переводом.
